# Running: slow sources, runs that go wrong, and runs to reuse

The part of `running.md` read before a job with a read from a data provider, when a run ends other than SUCCEEDED or a call errors, and before a run whenever this chat already holds a CleanPull run. The rest of the rules are in `running.md` and its other parts.

## Timing: sources from data providers

Some sources come from licensed third-party data providers that CleanPull holds the accounts for, under the providers' terms; CleanPull's actors don't read those sites themselves:
- **CleanPull's marketplace data service** (Bright Data, a web-data provider) is the source for eBay, Etsy, Walmart, Target, Best Buy, Home Depot and Lowe's searches and product pages, Target and Best Buy records by barcode, AliExpress and Alibaba searches, and Trustpilot reviews;
- **CleanPull's ad library service** (ScrapeCreators, an ad data provider) is the source for the Meta and TikTok ad libraries, and for Google's Ads Transparency Center items on a run where Google's own library returns none.

These reads are slower:
- **marketplace and supplier searches:** usually 1 to 4 minutes a run for Walmart, eBay, Home Depot and Lowe's, AliExpress and Alibaba (their search pages are read directly: AliExpress about 15 to 25 seconds a product idea, Alibaba about 35 to 80); up to about 12 minutes for Etsy, Target and Best Buy, and for the others when a page can't be read and the service reads the search the slow way; whatever the number of keywords; with Amazon in the same job, answer with Amazon first while the others run;
- **the AliExpress single-unit check** (`singleUnitCheck`): usually under a minute (it reads AliExpress's search page first: 3 products in about 30 seconds; its status message meanwhile is "Checking AliExpress…"). Only when that page read fails (rarely) does it fall back to the data service, which visits each product page: then 5 to 20 minutes, and while it waits the run's status message is "Waiting for AliExpress (usually 5 to 10 minutes)…"; after 20 minutes the run stops waiting on its own, and an idea AliExpress didn't answer comes back free, with the reason "AliExpress didn't answer within 20 minutes" (so it is never offered a stop at 13 minutes, as a slow provider search is). It needs at least 22 minutes of run time: never pass a `callOptions.timeout` under 1,320 seconds for it (leave it out, and the run keeps its default of 60 minutes);
- **Target and Best Buy by barcode:** 3 to 5 minutes a run;
- **product pages on those marketplaces:** a few seconds to a few minutes;
- **Trustpilot:** about 30 to 60 seconds a business.

Say so before the run ("this takes a few minutes"), even when the user has already said yes, start it with `waitSecs: 45`, and follow it with `get-actor-run` as above. Each such run also has a provider search fee per source (see `costs.md`), so group the user's items into one run rather than several.

**Never hold the whole answer for a slow read.** When a job mixes fast reads (Trends, Amazon, TikTok Shop, the ad libraries, Made-in-China) with a slower provider read (a marketplace or supplier search: an Etsy, Target or Best Buy search, and a Walmart, eBay, Home Depot, Lowe's, AliExpress or Alibaba search, which usually takes 1 to 4 minutes but can fall back to the slow way; and the AliExpress single-unit check when it is still running after its wait: below), start the slow one **first**, as its own run with `waitSecs: 0`, then the fast ones; answer as soon as the fast ones are in, naming the slow part as still reading ("still reading AliExpress (usually 1 to 4 minutes, up to about 12)"; for the single-unit check, "AliExpress is slow on this one (it can take 5 to 20 minutes)") and marking what depends on it as provisional; then follow the slow run with `get-actor-run` every 30 to 45 seconds (the single-unit check less often: below) and, when it lands, complete the answer in a **short follow-up message**: only what changed (the gate it settles, the verdict now final), never the whole answer again.

**The single-unit check, in that pattern.** It gets a real wait first, and that pattern applies only if it is slow. Say the time with the cost, before the run: "the AliExpress price usually takes under a minute". Start it first, with `waitSecs: 0`, and keep its run ID, then start the other reads (so it runs while they do). When the other reads are in, and before writing the answer, wait for it: `get-actor-run` on its run ID with `waitSecs: 45`, and once more with `waitSecs: 15` if it is still RUNNING (about a minute of waiting on top of the time the other reads took; 45 seconds is the most one call can wait, so a single `waitSecs: 60` isn't possible). Skip the wait when its `call-actor` or an earlier `get-actor-run` already returned it finished. **Read its status message before calling it slow:** while it is RUNNING with "Checking AliExpress…" at the start of its `statusMessage`, the fast read is still going (a page retry, a slow start), so wait on with `get-actor-run` `waitSecs: 45`, up to 2 more calls. Only a `statusMessage` that says "Waiting for AliExpress" (the actor has gone to its slow fallback), or a run still RUNNING after those calls, is the slow case below.
- **Finished by then (the normal case):** use its result directly, as one more read in the answer: gates 2 and 3 (the Marketplace lens's gate 2 and margin) are read from it through the lens files' rules as for any read that is in, with the actor's numbers and the final For you verdict. No "still reading" or "slow" note, no "(provisional)" mark on what reads from it, no follow-up message and no promise of one; that pattern is only for a check still running. A check that finished without an answer ("AliExpress didn't answer", `offersRead: 0`) is read as the lens files say, in the same answer.
- **Still RUNNING after that wait (the fallback, rare: the search-page read failed and the data service is visiting each product page, 5 to 20 minutes):** then, and only then, answer first and complete it in a follow-up, as the rest of this point sets out. **A check covering several ideas** (find-products' top 3) stays RUNNING while any one of them is slow: first read the rows it has already written (`get-dataset-items` on the run's dataset); an idea whose single-unit row is already there is finished and read as in the normal case, and only the ideas still missing are marked slow and completed in the follow-up. Say why in one line: "AliExpress is slow on this one (it can take 5 to 20 minutes); I'll answer now and add it when it lands." The first answer marks what reads from it as provisional (the lens files say which: the cold-traffic lens's gates 2 and 3, the Marketplace lens's gate 2 and margin), each named in the For you lines or the fit check as "AliExpress is slow on this one (it can take 5 to 20 minutes)" ("Gate 2, single units: AliExpress is slow on this one (it can take 5 to 20 minutes)"; the same for gate 3), not only through the verdict's "(provisional)" mark, which comes on top. **The first answer is not the end of the turn.** Right after writing it, keep following the check's run in the same turn and write the follow-up when it lands, or say it missed at 20 minutes. Never write "I'll post a follow-up" and stop: once the turn ends, nothing happens until the user writes again. If for any reason you have to stop before it lands, say so plainly: "AliExpress is still loading; send any message and I'll add it." **Following it:** after the first answer, call `get-actor-run` with `waitSecs: 45` back to back, with no other tool calls in between, until it returns or misses at 20 minutes. Each call waits up to 45 seconds for the run to finish (there is no other way to wait), so a 10-minute fallback takes about 13 calls. **A check already in flight:** if this conversation already started a single-unit check for the same idea and it is still running, follow that run by its run ID instead of starting another ("Running": never call `call-actor` again for the same job). When it lands, the follow-up gives those parts with the actor's numbers and the final For you verdict, saying plainly when the label changed ("now: a strong fit", "now: a fit, with one fix") or that it stands. A run that ends without an answer ("AliExpress didn't answer within 20 minutes") is completed the same way, with the lens's no-answer note and one rerun offered.

## When a run goes wrong

**Actors not public yet.** A table in `costs.md` that starts with **Pending** is for an actor CleanPull hasn't published yet. If its run fails because the actor isn't found, say plainly that this part of the job is coming soon, give what the other steps found, and don't retry.

| What happened | What to do |
| --- | --- |
| **ABORTED with results** (usually the cap) | Show what was read and what it cost. Work out from `RUN_SUMMARY` which items weren't read, estimate a rerun of **only those** (pass just those items, or `maxItems` for the rest), and get a new yes. |
| **FAILED, "Actor not found"** | The actor isn't public yet (see "Actors not public yet"): say this part is coming soon, give the other steps' results, don't retry. |
| **Memory limit** (Apify refuses the start for the account's memory) | Nothing ran or was charged. Apify limits the total memory of the actors running in an account at once (8 GB on the free plan at the time of writing; the user's plan may differ). Start the runs one after another instead of together, or wait a few minutes for the running ones (often a scheduled digest), and say so. |
| **Usage limit reached or account blocked** (a run or scheduled watch doesn't start, or fails at once, with a message about the account's monthly usage, credit or limit) | Nothing ran or was charged. On Apify's free plan, once the month's USD 5 of usage is spent, Apify blocks the account's runs until the next monthly cycle, scheduled watches included, so they go quiet; on a paid plan, a usage limit the user set stops runs the same way. Say so plainly, with the reset date if the message gives one, and that the plugin can't see the account's balance. Only a message says this: never infer it from runs that look old or missing (a paused schedule, a changed time or a test account look the same); when the user asks why a watch hasn't run, it can be named as one possible cause among those. Offer the ways forward: wait for the new cycle, raise the limit or move to a paid plan on the Console's Billing page (`https://console.apify.com/billing`), or slow or pause watches (`watchlists`) so the next month fits. Don't retry. |
| **A data provider was unavailable** (`RUN_SUMMARY` names the items not read, uncharged) | Say which items. For a watch, they are read on the next run; for a one-off, offer a rerun of only those items later. |
| **A site couldn't be read** (a page with no product data, a store that didn't answer, a site the actor doesn't cover) | Name it and the reason from `RUN_SUMMARY`, uncharged. Suggest another way in: the barcode instead of the page, the product's page on another store, or the brand's own site. |
| **A slow provider search** | Poll every 30 to 45 seconds and say how many minutes it has run. After 13 minutes, offer to stop it with `abort-actor-run`: what was read so far stays, and only that is charged. **Except the AliExpress single-unit check:** followed as "Timing" says, with no stop offer at 13 minutes; it stops on its own at 20 minutes, and an idea it missed is free. |
| **FAILED or TIMED-OUT, other reasons** | Read `RUN_SUMMARY` or the status message; say plainly what went wrong and what would fix it (a wrong URL, a marketplace not supported). Rerun only with a yes. |
| **A tool error or dropped connection** | Never start the same job again straight away: find the run first (see "Running"). |

## Runs in this conversation: what reuses what

After every run, keep in mind (from its tool result): the actor, a short input summary (keywords, domains, ASINs, marketplace), `defaultDatasetId`, `defaultKeyValueStoreId`, when it finished and what it cost.

Before any run in a chat that already holds a CleanPull run, look back through it for a run that already holds what's needed (`running.md`'s "Runs in this conversation"):

| Later job | Reuses | Saves |
| --- | --- | --- |
| `gaps` after `spy-store` on the same store | the Shopify dataset | about USD 0.20 a store |
| `validate` after `find-products` | TikTok rows and the Trends record for the same keyword | USD 0.06 to 0.09 |
| `validate` after `market-scan` | the keyword summary | USD 0.017 |
| `validate` after `market-scan` (an Etsy or eBay seller, listing rows read) | that marketplace's keyword summary and listing rows for the same keyword (same day; not when that scan had `ebayFixedPriceOnly: true`, a filtered sample) | about USD 0.10 and up to 12 minutes |
| `validate` after `find-products` (an Etsy or eBay seller) | that marketplace's keyword summary and listing rows for the same keyword (same day) | about USD 0.10 an idea and up to 12 minutes |
| `validate` after `find-products` (dropship) | the AliExpress single-unit check for the same idea, unless `validate` would send a different `marginCheck` (a planned price, ad cost or card fee given since: then it runs again) | about USD 0.04 an idea |
| `validate` after `find-products` (cold traffic) | the Where you'd compete advertiser rows for the same idea and country | about USD 0.05 an idea |
| `reviews-watch` after `spy-store` | the best sellers' URLs | a question |
| `listing-audit` after `rank-watch` | `outrankedBy` URLs as `competitorUrls` | a question |
| `price-watch` after `price-check` | the same URLs and ASINs as items (not a baseline: a different actor and monitor); Walmart, Target, Best Buy, eBay and Etsy pages read the same day skip the baseline run, and the first scheduled run records them (`price-watch`, "Same-day marketplace pages") | a second confirm; about USD 0.0045 a page and USD 0.015 a marketplace |
| `launch-plan` after `validate` | the Amazon leaders (ASINs, fees, ratings), the keyword summary, the supplier summary, and the leaders' complaints if read | about USD 0.08 |
| `export` after anything | the dataset ID | a question |

**Fresh enough:** prices, stock, Buy Box, ranks and promotions the same day; catalogues, review summaries and ads 7 days; Trends, supplier prices, listing audits and tech stacks 30 days. Say "from your check at 09:12 today" when you reuse one, and offer a fresh read if the user wants it.
